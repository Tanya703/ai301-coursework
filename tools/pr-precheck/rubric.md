# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| `diff-matches-plan` | Every changed file and hunk in the diff, read against the plan's scope line, approach, file list, not-in-scope line, and deviation notes (live mode: `git diff main...HEAD` against `plan.md` and its `## Deviations`); plus every piece of work the plan commits to, looked for in the diff | Two directions, both must hold. (1) Nothing extra: every hunk is the planned fix, a test the plan names (or a regression test for the fix), or the smallest supporting edit the fix needs to compile or run (an import it uses, a new message string it shows, a test helper it calls). A hunk that adds behavior, options, flags, settings, renames, refactors, or rewrites the plan never named fails, and so does one doing something the plan's not-in-scope line excludes, unless a deviation note in the plan or the description names it and says why. (2) Nothing silently missing: every piece of work the plan commits to (each file, each step, docs, changelog, tests) is in the diff, or its absence is stated as a deferral in the plan or the description. A disclosed shortfall passes. | required |
| `description-matches-diff` | Each factual claim in the PR title and description about what the change does or contains (files touched, "docs updated", "changelog entry added", "tests added", "exactly as planned", "no changes outside X", "no functional changes"), read against the diff | Every claim the description makes about the change is true of the diff. A fidelity claim ("implements the plan exactly", "no other changes", "nothing beyond the plan") fails when the diff contains any hunk `diff-matches-plan` would call extra. A claim that something was added or updated (docs, changelog, a test) fails when the diff contains no such change. A description that is silent passes this check; only false claims fail it. | required |
| `evidence-is-decisive` | The test-evidence section (and any before/after in the description), read against the plan's test plan and the repro evidence's failing steps (live mode: `test_evidence.md` against `plan.md`'s test plan and the unit-2 repro) | The evidence re-runs the plan's repro (the same failing input or scenario the issue and plan name) on the branch, and shows an observable after result (output, exit code, value, rendered state, test assertion on the fixed behavior) that differs from the before. The before may come from main or from the plan's repro evidence. When the plan's test plan names more than one failing scenario, each one is shown re-run; controls the plan expects to stay unchanged may simply be stated unchanged. Fails when the evidence is a claim without output ("tested locally", "works on my machine", "verified working for a day"), only a suite result ("tests pass") with no repro re-run, only a control or a different input that never exercised the bug, or a named failing scenario of the plan left un-run. | required |
| `repo-checks-reported` | The test-evidence section and description, read against the checks the plan's test plan names and the checks the repo facts / PR template / contributing guide ask for (live mode: `make test-unit`, `make test-integration`, `make lint`, `make typecheck` from Path Review's template) | The outcome of the repo's own test suite or checks named in the plan or repo facts is reported with the command or suite named and its result. A failing or empty check reported honestly with its reason (for example "no tests ran" where the repo has none yet) passes. Fails when no repo check outcome appears at all, or when a check the repo or plan explicitly names is silently missing. | required |
| `diff-is-clean` | Every hunk of the diff, plus the commit list (live mode: `git diff main...HEAD` and `git log --oneline main..HEAD`) | The diff carries only the change and its tests. Fails if any hunk adds: a debug print or log line (`print`, `eprintln!`, `console.log`, `DEBUG`), commented-out code (an earlier attempt or disabled line kept in a comment), a dead or unused function, variable, or `allow(dead_code)`/`noqa` to keep one, a TODO/FIXME unrelated to the fix, formatting/whitespace/re-indent or import-reordering churn on lines the fix does not otherwise change, or an unrelated hunk. Comments explaining the fix are not debris. Commit messages like "wip" or "misc cleanups while debugging" are supporting evidence, never a fail on their own. | required |
| `template-asks-met` | The repo facts block's PR template sections and checklist items, and any PR requirement the contributing guide states (a closes/fixes line, a changelog or whatsnew entry, a required title convention), read against the title, description, and diff (live mode: `.github/PULL_REQUEST_TEMPLATE.md` and `docs/CONTRIBUTING.md` against `pr_draft.md` and the diff) | Every section the template asks for is present with real content about this change (not left as placeholder text), every checklist item is addressed (ticked truthfully or explained), a required issue-link line is present with the issue number, and a required entry file (CHANGELOG, whatsnew, release note) is in the diff. Where the repo has no template and states no PR requirement beyond general advice ("keep PRs small", "add tests"), this passes. Asks about tests and test results are graded by the evidence checks, not here. | required |
| `ai-disclosure-meets-policy` | The repo facts block's contribution / AI policy line (live mode: `docs/CONTRIBUTING.md`, any AI policy file, and the course rule that every PR discloses AI use in Notes for Reviewers), read against the description | Every package is AI-assisted work. Where the repo's policy requires disclosing AI use, the description discloses it, including the tool and extent where the policy asks for them. Where the policy only sets conditions without requiring disclosure, or states no AI policy, this passes with nothing extra required. | required |
| `title-names-change` | The PR title, read against the diff | The title says what the change does in terms a reviewer could check against the diff (component plus behavior), not "fix bug" or "update file". | preferred |

## Verdict rule

`accept` if and only if every `required` check grades `pass`. A single
`required` check graded `fail` holds the package: `reject`.

`unclear` on a `required` check counts as `fail`: a PR a grader cannot
verify from the package is not ready to submit, and the fix is to put
the missing fact into the PR.

`preferred` checks never change the verdict; they are reported so the
author can see what would make a ready PR better.

Doing less than the whole issue is not a fail by itself. A shortfall
or deviation stated in the plan's notes or the PR description is graded
as disclosed scope, and the PR is judged on what it claims. Length,
polish, and formatting of the description never move a grade.
